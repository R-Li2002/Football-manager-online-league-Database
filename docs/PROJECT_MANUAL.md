## 补充：P1 后台写操作骨架收口（2026-03）

为降低后台继续新增管理动作时的重复开发成本，当前已开始按低风险方式收口后台写操作模板：

  - 变更后 transfer log 落库

  - 失败回滚
- `services/admin_write_actions.py` 继续负责后台接口级审计包装，但不再自己承载底层变更骨架。
- `services/transfer_service.py` 与 `services/roster_service.py` 已将核心单动作逐步改为返回统一 mutation 结果，再由 runner 处理公共收尾逻辑。
- `services/roster_service.py` 中原先函数内临时导入 `create_transfer_log` 的写法已清理，避免局部隐藏依赖。
- `services/league_service.py` 继续保留：
  - `recalculate_team_stats()` 作为“可选 commit”的底层统计刷新函数
  - `persist_with_team_stats()` 作为“刷新统计并提交”的统一持久化入口
- `services/admin_service.py` 当前仅作为兼容聚合层，避免旁路直接绕过统一后台写入口。

这一轮收口的目标是把“查对象 -> 变更 -> transfer log -> team stats -> commit -> 审计响应”拆成更清晰的责任边界，而不是改变现有管理后台接口协议。

当前后台写动作约定如下：

- `services/admin_write_actions.py`
  - 负责后台接口级包装。
  - 负责把 request 转成审计 payload，并调用 `execute_admin_action()`。
  - 允许记录成功/失败审计。
  - 不负责业务对象变更。
  - 不负责直接 `db.commit()`。
- `services/transfer_service.py` / `services/roster_service.py`
  - 负责查对象、校验、修改 ORM 对象、整理 transfer log 参数、声明受影响球队和统计 scope。
  - 单动作函数应优先返回统一的 `AdminMutationResult`，再交给 runner 处理公共收尾。
  - 这些函数默认不应自己写审计。
  - 这些函数默认不应自己直接 `db.commit()`。
  - 如需撤销逻辑等特殊辅助函数，应尽量只做对象回滚和 scope 计算，不重复提交策略。
- `services/admin_action_runner.py`
  - 负责统一管理员校验。
  - 负责统一执行 mutation 后的公共收尾：
    - transfer log 落库
    - 团队统计刷新
    - 最终 `commit`
    - 管理后台文本日志写入
  - 负责在异常时统一 `rollback`，保证失败动作不留下半完成状态。
- `services/league_service.py`
  - `recalculate_team_stats()` 是底层统计刷新函数。
  - 只有显式传入 `commit=True` 时才允许在内部提交。
  - `persist_with_team_stats()` 是“刷新统计并提交”的统一入口，供后台写动作公共收尾调用。

推荐的新增后台写动作实现顺序：

1. 在 `transfer_service.py` 或 `roster_service.py` 中实现对象变更与 `AdminMutationResult` 拼装。
2. 如动作需要 transfer log，则只声明 log 参数，不在动作函数里单独落库提交。
3. 在 `admin_write_actions.py` 中增加对应包装项，复用统一审计入口。
4. 补单测，优先验证：
   - 失败时是否回滚
   - 是否写入正确 transfer log
   - 是否刷新受影响球队统计
   - 是否维持外键 / 引用一致性

当前球员流转中，“大海海捞”使用独立的 `POST /api/admin/sea-fish`：球员只要不属于超级、甲级或乙级球队，即统一视为“大海球员”并允许海捞；尚未进入联赛 `players` 表、但存在于球员属性数据库中的 UID 也可直接海捞，系统会以属性数据库 CA 同时初始化其初始 CA 与当前 CA，并带入基础资料。目标必须是三级联赛球队。隐藏球队统一命名为“大海”，数据库迁移会把旧“85大海”及其他非三级联赛球员归入该球队。该动作与旧 `POST /api/admin/fish` 的手工创建语义分离；撤销新海捞会将球员送回大海并恢复原 CA，撤销旧海捞仍删除当时创建的球员。

当前约定下，允许直接 `commit` 的位置只有两类：

- `admin_action_runner.py` 中统一收尾时
- `league_service.py` 中显式设计为持久化入口的 helper，例如 `persist_with_team_stats()`

除这两类之外，后台写动作函数应尽量只修改对象状态，不单独决定提交时机。

- `imports_runtime.persistence.run_import()` 在成功解析 `联赛名单` 后，会先执行名单 upsert，再按本次 Excel 中出现过的 UID 集合清理 `players` 表里已经不在新名单中的旧球员。

- 球队人数、门将数、名额占用、工资与最终工资缓存会在清理后的最终名单基础上重算，因此网站展示应与当次 Excel 名单保持一致。
- `player_attributes` 与 `player_attribute_versions` 仍按属性版本库语义维护，不因为联赛名单缺少某个 UID 就删除历史属性记录。

这一约定的目的，是避免旧名单球员残留在 `players` 表中，继续污染球队名单页、球队人数和工资统计。

## 补充：属性版本默认选择与缓存排障（2026-04）

当前属性库的版本选择约定如下：

- `/api/attributes/versions` 会返回 `available_versions` 与 `default_version`
- `default_version` 由 `repositories/attribute_repository.py` 结合 `attribute_versions.py` 统一按“数值最新优先”计算，例如 `2630` 应覆盖 `2620`
- 前端数据库页、详情页和排行榜筛选都应从该接口读取默认版本，而不是在页面脚本中硬编码某个历史版本号

当前线上排障经验如下：

- 如果接口 `GET /api/attributes/versions` 已返回最新版本，但页面仍默认查询旧版属性库，优先排查浏览器缓存和静态资源版本，而不是直接怀疑数据库
- 如果属性搜索页长时间停留在“搜索中”，应先检查 `/api/attributes/versions` 与 `/api/attributes/search/...` 的实际状态码和返回体，再判断是前端缓存问题还是后端数据问题
- 当前已知的一类后端数据问题是历史属性记录 `ca / pa` 为空；现有 `services/read_presenters.py` 已统一兜底为 `0`，避免单条异常记录中断整批查询响应

## 补充：球员库高级搜索模式（2026-04）

当前球员库公开查询已在原有 `GET /api/attributes/search/{player_name}` 之外，新增高级搜索接口：

- `POST /api/attributes/advanced-search`
- 请求体支持：
  - `query`
  - `version`
  - `age / ca / pa` 的 `{min,max}`
  - `attributes` 范围字典
  - `positions` 列表，每项为 `{position,min_score}`
  - `limit`
- 响应当前返回：
  - `items`
  - `data_version`
  - `limit`
  - `truncated`
  - `applied_filters_summary`

当前实现约定如下：

- 空关键词允许搜索，但必须至少存在一个高级筛选条件；不允许“空关键词 + 无条件”直接全库拉取
- 仓库层对高级筛选字段使用 allowlist，只允许对白名单属性字段和位置字段生成过滤条件
- 位置筛选当前固定按 AND 语义处理；例如同时要求 `ST >= 15` 与 `AMC >= 15` 时，球员必须同时满足这两个位置阈值
- 为避免一次返回过大结果集，高级搜索当前默认上限为 `200`；命中过多时响应会返回 `truncated=true`
- 数据库页会把高级搜索条件纳入 SPA history capture / restore；切换属性版本、从详情页返回和浏览器前进后退时，都应保留高级筛选上下文

## 补充：比赛驱动积分榜与赛程（2026-06）

当前积分榜采用“赛程 / 比赛结果为事实源，积分榜实时计算”的方案：

- 赛程原始文件放在 `imports/schedules/`，例如 `imports/schedules/86届赛程 (2).xlsx`
- 当前导入器支持工作簿按 `超级赛程 / 甲级赛程 / 乙级赛程` 分 sheet 的块状格式
- 每个轮次块按 `主队 / vs / 客队` 识别；导入时会写入 `matches` 表
- 同一场比赛按 `级别 + 轮次 + 主队 + 客队` 匹配，重复导入会保留已有比分和状态
- 未赛、延期、取消比赛只展示在赛程中，不参与积分榜计算
- 已赛比赛必须有双方比分，并按胜 3 分、平 1 分、负 0 分计算积分榜
- 默认排名规则为：积分、净胜球、进球数、胜场、球队名
- 积分榜响应中同时返回总战绩、胜率、主场战绩和客场战绩
- 积分榜响应同时返回赛季排名预测。`services/standings_prediction_service.py` 按真实剩余对阵执行 1,200 次确定性赛季模拟，当前积分、净胜球、胜场和主客场表现决定球队状态，并通过六场中性先验压低赛季初少量偶然赛果的影响。每队返回最可能名次、90% 预测区间、预测置信度、冠军/前二/前五/后五概率和竞争标签；每级别另返回赛季初段、中段、后段、收官冲刺或最终阶段摘要。
- 预测区间会随剩余比赛减少自然收束；赛程尚未导入时统一显示第 1 名至该级别末位的宽区间，全部赛程结束后预测名次和区间严格等于最终排名。模拟结果按积分榜数据与剩余赛程指纹缓存 90 秒，比分或赛程变化会自动形成新缓存键，无需数据库迁移或人工刷新预测数据。
- 前端默认用颜色标识每个级别的前五升级区和后五降级区
- 积分榜前端样式参考 `imports/examples/rankexample.png`，使用 `总数据 / 主场数据 / 客场数据` 分组表头，并保留主教练和队伍标识列

公开读接口：

- `GET /api/matches`
  - 可选参数：`level`、`round_no`
  - 返回各级赛程、轮次和比赛列表
- `GET /api/standings`
  - 返回按级别分组后的积分榜行

后台写接口：

- `POST /api/admin/matches/import`
  - 从 `imports/schedules/` 自动选择最新 Excel 赛程文件导入
  - 操作会进入 `competition/import_schedule` 审计分类
- `PATCH /api/admin/matches/{match_id}`
  - 管理员可编辑比分、状态、日期和备注
  - 操作会进入 `competition/update_match_result` 审计分类

赛程维护账号：

- `admin_users.role` 当前支持 `admin` 与 `schedule_editor`
- `admin` 保留完整维护权限
- `schedule_editor` 只允许访问 `POST /api/admin/matches/import` 与 `PATCH /api/admin/matches/{match_id}`
- 启动时可通过环境变量 `HEIGO_SCHEDULE_ADMINS` 创建赛程维护账号，格式为 `username=password;username2=password2`
- 已存在账号不会被覆盖密码；如需调整密码，应通过维护脚本或数据库管理流程显式修改

前端入口：

- 主导航新增 `积分榜`，位置在 `联赛名单` 和 `球员库` 之间
- 页面内通过二级切换展示 `积分榜 / 赛程`
- 页面内通过 `超级 / 甲级 / 乙级` 按钮切换级别
- 管理员登录后，赛程行会显示比分与状态编辑控件，保存后重新加载赛程和积分榜
- 当前结果区会显示关键词 / 高级条件 chips，并提供“一键清空高级条件”入口；这部分属于数据库页搜索体验的一部分，不应绕开 `database.search.js` 再做平行实现

## 补充：伤停统计模块（2026-06）

伤停统计位于主站 `数据统计` 模块下，作为 `积分榜 / 赛程 / 球员榜 / 伤停` 的第四个二级页签。

数据模型：

- 当前伤停状态保存在 `player_suspension_records` 表，每名球员最多一条当前记录。
- 字段包含球员 UID、球员名、球队、级别、黄牌数、红牌停赛、红伤停赛和工作人员备注。
- 黄牌数允许 `0-3`；累计三张黄牌视为停赛。
- 红牌停赛和红伤停赛为独立布尔状态，任一为真时该球员进入停赛栏。
- 当黄牌数为 0、无红牌停赛、无红伤停赛且备注为空时，后台保存会自动清除该球员的伤停记录。

公开读接口：

- `GET /api/suspensions`
  - 返回 `超级 / 甲级 / 乙级` 下每队的伤停聚合。
  - 每队分为 `one_yellow`、`two_yellows`、`suspended` 三组。
  - 每队同时返回从球员备注汇总出的 `notes` 列表。

后台写接口：

- `PATCH /api/admin/suspensions`
  - 权限与赛程维护一致，允许 `admin` 和 `schedule_editor` 维护。
  - 请求字段包括 `player_uid`、`yellow_cards`、`red_card_suspended`、`red_injury_suspended`、`notes`。
  - 后端会校验球员必须属于 `超级 / 甲级 / 乙级` 的可维护球队。
  - 操作会进入 `competition/update_suspension_record` 审计分类。

前端交互：

- 伤停页继续使用 `超级 / 甲级 / 乙级` 级别按钮切换，不展示杯赛级别。
- 公开用户可查看每队 `1张黄牌 / 2张黄牌 / 停赛` 三栏和备注。
- 工作人员登录后，每队卡片底部出现录入行。
- 球员输入使用队内球员 `datalist` 自动补全；输入球员名开头或 UID 后保存。

## 补充：容器更新与静态资源缓存经验（2026-04）

当前部署与排障中应注意以下边界：

- 宿主机 `/srv/heigo` 的源码更新并不会自动更新运行中的 `heigo` 容器；正式生效仍依赖 `docker compose build heigo` 与 `docker compose up -d heigo`
- 如镜像重建暂时受阻而必须应急排障，可以临时把修复过的源码 `docker cp` 进运行容器后重启主站；但这种热修只应作为恢复手段，后续仍应补一次正式镜像重建
- 当前前端静态资源查询参数由根目录 `VERSION` 注入；如果后端接口已正确返回最新属性版本或新工资帽规则，但浏览器仍表现为旧逻辑，应优先怀疑静态资源缓存，处理方式是强制刷新，或在发布时同步提升 `VERSION`
- 主站通过 `GZipMiddleware` 压缩大于 1KB 的响应；带 `?v=<VERSION>` 的 `/static/` 资源使用一年期 `immutable` 缓存，未带版本号的静态资源只使用短缓存
- 主站 UI 使用 Apple / Windows / Android 系统中文字体栈，不应在全站 CSS 中引用十余 MB 的完整中文字体文件；站点 Logo 等首屏图片应按实际展示尺寸提供网页优化版本
- 主站 CSS 按固定顺序加载：`app.css`（尚未迁移的历史规则）→ `css/ui-foundation.css`（变量与公共交互）→ `css/shell.css`（品牌区域、桌面主导航、顶部工具、账号菜单与页脚）→ `css/pages/*.css`（页面唯一所有权）→ `css/responsive.css`（移动底栏、更多菜单及已迁移模块的最终响应式规则）。当前 `pages/database.css` 独占球员搜索、候选名单、战力榜、战术板、互动榜、球员详情与对比，`pages/competition.css` 独占数据统计与杯赛规则，`pages/team.css` 独占球队中心、联赛概览及 `.team-cup-*`；已迁移选择器不得重新追加到 `app.css`，新增或迁移规则应先确定唯一归属，并同步维护 `test_frontend_css_layers.js` 的所有权约束
- 教练主页链接的 HTML 渲染器常驻于 `static/app.js`，供积分榜、伤停、联赛概览和球队中心直接使用；链接点击后再通过 `ensureAppModule('coaches')` 加载完整教练模块。功能模块不得直接调用只存在于另一个懒加载脚本中的全局函数，否则刷新直达页面时会出现依赖未定义。数据统计的接口请求错误与页面渲染错误应分别捕获和提示。

## 补充：数据统计模块与杯赛淘汰赛（2026-06）

当前主导航中的 `数据统计` 统一承载比赛与榜单相关功能，二级页签包括 `积分榜 / 赛程 / 球员榜 / 伤停`。

级别切换分为两类：

- 联赛级别：`超级 / 甲级 / 乙级`
- 杯赛级别：`冠军杯 / 联盟杯 / 无铭剑杯`

联赛赛程的比赛数据编辑窗口按球员位置展示名单，固定顺序为 `前锋 → 边锋 → 中场 → 后腰 → 后卫 → 门将`。复合位置按能够胜任的最靠前位置归类，同一位置组内按姓名排序；只有历史比赛事件、但已不在当前名单且缺少位置信息的球员放在末尾。

杯赛阶段实现如下：

- 冠军杯小组赛固定为 5 组、每组 6 队；联盟杯小组赛固定为 4 组、每组 6 队
- 杯赛赛程页直接使用“小组赛分组 / 小组赛赛况”两个一级入口，不再嵌套“小组赛阶段 / 淘汰赛阶段”；每组 6 队完整后自动生成 10 轮、30 场主客场双循环赛程，同组任意两队互换主客场各赛一场。轮次按连续主客场排列：奇数轮为首回合，紧接的偶数轮立即交换主客场；赛况页全宽展示全部对阵并只维护双方进球数，不录球员事件
- 小组积分榜独立放在积分榜页面，与淘汰赛阶段并列为一级入口；每组排名按胜 3、平 1、负 0 计算，并集中展示晋级去向和跨组资格概览
- 冠军杯每组前三名与五组中成绩最好的小组第四共 16 队晋级冠军杯淘汰赛；其余四个小组第四转入联盟杯淘汰赛
- 联盟杯每组前三名共 12 队晋级，与冠军杯转入的四支球队组成联盟杯 16 强；跨组第四名依次按积分、净胜球、进球数和球队名比较，小组赛未全部结束时所有去向标记为“暂列”
- 冠军杯：从 16 强开始，阶段为 `1/8淘汰赛 / 1/4淘汰赛 / 半决赛 / 决赛`
- 联盟杯：从 16 强开始，阶段同冠军杯
- 无铭剑杯：从 32 强开始，阶段为 `1/16淘汰赛 / 1/8淘汰赛 / 1/4淘汰赛 / 半决赛 / 决赛`
- 对阵图采用中心对称布局，左右两侧为早期淘汰赛，中间为决赛和冠军区域
- 奖杯图标来源为 `imports/trophy/`，当前对应资源为 `champion.png`、`league.png`、`FA.png`

- 冠军杯和联盟杯按主客场两回合处理
- 无铭剑杯从半决赛和决赛开始按两回合处理
- 总比分相同时，系统需要支持按客场进球规则确认晋级方；前端保存比分时应提示维护者补充客场进球优势方

维护权限：

- 杯赛球队编辑、比分编辑和初始化权限沿用赛程维护权限

- 冠军杯和联盟杯小组名单通过 `cup_group_teams` 保存，按杯赛、小组和槽位唯一；同一球队在同一杯赛中只能出现一次

## 补充：数据统计工作闭环（2026-07）

数据统计页在公开浏览能力之外，为拥有 `schedule.write` 或 `suspensions.write` 的工作身份提供当前轮次工作面板。普通公开用户不显示维护面板和确认操作。

轮次范围：

- 联赛工作按双轮周期管理，例如 `第 1-2 轮`、`第 17-18 轮`。
- 系统优先选择已经开始录入但尚未确认完成的最新双轮周期；没有已开始轮次时选择最早赛程周期。
- 工作台只统计三个级别的当前工作周期，不再把全部未来 `scheduled` 比赛作为当前待办。

完成度实时计算：

- 比分完成：比赛为已赛、判负、延期或取消等已处理状态；正常已赛必须有完整比分。
- 事件完成：正常比赛的进球事件总数等于总比分、助攻不超过进球，并且恰好有一名最佳球员。
- 判负、延期和取消比赛不强制录入进球、助攻或最佳球员。
- 数据异常和缺失任务由 `services/competition_work_service.py` 统一计算，前端只负责展示和定位，不维护平行判断。

轮次状态：

- `competition_responsibility_assignments` 保存超级、甲级、乙级的长期职责，每个级别分别设置 `schedule`（赛程与比赛事件）和 `suspensions`（伤停）负责人。
- `competition_round_work_states` 只保存伤停确认、提交复核与最终完成状态，不复制比分或球员事件，也不再要求逐轮任命负责人。
- 新轮次按 `待任命 → 处理中 → 待复核 → 已完成` 流转；赛程与比赛事件负责人负责提交，完整管理员负责最终复核。
- 可任命对象包括完整管理员、拥有对应权限的赛事工作人员，以及启用对应权限的教练工作账号；同一账号可以兼任多个级别或两类职责。
- 普通工作账号只能修改自己负责级别的数据。完整管理员保留三个级别的全局维护、任命和复核能力。
- 工作账号和教练工作账号的“我的任务”及指标按自己的级别职责统计；伤停负责人不会收到其他级别或赛程事件待办。
- 伤停记录在确认后发生修改，会自动撤销当前轮次的伤停确认。
- 提交复核或完成后，相关比赛或球员事件再次变化时会自动退回处理中，并要求重新提交。
- `competition_round_work_logs` 保存负责人变更、伤停确认、提交、退回和复核记录；相关高层操作同时写入 `operation_audits`。

工作接口：

- `GET /api/workspace/competition-work`：返回三个级别当前工作周期的完成度和逐场任务。
- `PATCH /api/workspace/competition-responsibilities/{level}`：完整管理员任命该级别的赛程与比赛事件负责人、伤停负责人。
- `PATCH /api/workspace/competition-work/{level}/{round_start}/assignment`：兼容旧入口，仅映射为该级别赛程与比赛事件职责设置。
- `PATCH /api/workspace/competition-work/{level}/{round_start}/suspensions`：确认或取消当前周期伤停核对。
- `POST /api/workspace/competition-work/{level}/{round_start}/submit`：负责人执行完整校验并提交管理员复核。
- `POST /api/workspace/competition-work/{level}/{round_start}/review`：完整管理员复核通过或填写原因退回修改。
- `POST /api/workspace/competition-work/{level}/{round_start}/complete`：保留的兼容入口，仅可对已提交待复核任务执行通过。

前端维护约定：

- 工作面板提供缺比分、缺球员事件和数据异常三个精确任务入口。
- 自动保存必须显示 `有未保存修改 / 保存中 / 已保存 / 保存失败` 状态；保存失败不得清空当前输入。
- 工作筛选、数据统计页签、级别、轮次和球员榜类型进入浏览器历史与 URL 状态。
- 从工作台指标进入数据统计时，应落到对应任务筛选，而不是只打开赛程首页。

## 补充：统一数据状态与更新时间（2026-07）

全站数据状态由 `services/data_status_service.py` 统一计算，公开接口为 `GET /api/data-status`。页面只渲染服务端结果，不在各模块维护另一套完整度判断。

覆盖范围与口径：

- 联赛名单：结合当前三级联赛球队、球员数量和最近一次正式名单导入审计，显示来源文件与更新时间；已有数据但缺少正式导入审计时明确标记“状态未知”。
- 球员数据库：显示当前默认属性版本、版本球员数和最近一次属性导入审计时间。
- 赛程：三级联赛分别计算；活动轮次取最高非 `scheduled` 轮次，只检查已经开始的进度，未来已导入但尚未开赛的轮次不算待补。连续完成轮次从第 1 轮开始，正常已赛必须有完整比分，判负、延期和取消视为结果已处理。
- 积分榜：直接继承同级别赛程/赛果状态，并标明随赛果实时计算；工作台不重复把积分榜列成第二条赛程待办。
- 球员榜：复用比赛事件完整度；正常已赛要求进球事件总数与比分一致、助攻不超过进球且恰好一名最佳球员，事件数量异常不污染赛程/积分榜状态。
- 伤停：应更新轮次继承同级别赛程连续完成轮次。`site_notes.round_no` 保存 `0–34` 的结构化轮次；球队备注有轮次时优先使用，否则回退到级别备注轮次，落后的球队数量形成更新提醒。

状态枚举固定为 `normal / pending / stale / error / unknown`，前端必须同时使用线性图标、中文状态文字和说明，不得只依赖颜色。状态条位于联赛名单、球员库及数据统计当前子页；点击可直达对应模块、级别和二级页签，读取失败时提供可点击重试。联赛工作台仍是独立后台模块，只在现有“我的工作”页增加“数据状态”摘要，不与球队中心合并；普通工作人员按 `schedule.write` / `suspensions.write` 权限过滤，完整管理员查看全部可操作提醒。

机器人暂不消费该接口；需要接入时应复用同一服务端状态，不另建基于天数的机器人判断。

## 补充：FCLOGO 队徽匹配中心（2026-07）

队徽匹配属于“联赛工作台”后台能力，不属于球队中心。仅完整管理员可访问工作台的“队徽匹配”视图，按以下流程操作：选择三级联赛球队、选择 FCLOGO 检索或本地上传来源、预览候选、对照当前与候选队徽、勾选人工核对并二次确认。系统永不自动覆盖现有队徽。

- 采用端点：`POST /api/admin/team-logo-match/apply`，客户端只提交 FCLOGO slug 与展示元数据，不能提交任意 SVG 下载 URL

- SVG 最大 5MB，拒绝 DOCTYPE/ENTITY，移除脚本、嵌入对象、事件属性、外部 href、外部 CSS URL 与 data URL；清洗后保留 SVG，并通过 CairoSVG/Pillow 生成透明 512×512 WebP 作为 `Team.logo_path`
- `team_logo_sources` 保存来源页、来源名称、年份、类型、SVG/WebP 路径、SHA-256、搜索词、匹配分数、操作人和时间；再次匹配时保留历史来源文件与记录
- 上游搜索、下载、SVG 校验或转换失败时事务回滚，原队徽路径保持不变

## 补充：教练主页、账号、荣誉和助教团队（2026-06）

## 补充：每日日报与群聊播报（2026-08）

- 日报由 `services/daily_report_service.py` 统一生成，公开入口为 `GET /api/daily-report?report_date=YYYY-MM-DD`；首页仪表盘复用同一服务，不在前端重复拼接文案。
- 日报接口额外返回 `focus_content`、`image_url`、`fixture_group_count` 和 `focus_count`。`focus_content` 是机器人使用的浓缩头版；`GET /api/daily-report/image?report_date=YYYY-MM-DD` 由 `daily_report_image_service.py` 直接把完整日报渲染为 1200px PNG，缓存位于 `HEIGO_SHARE_CACHE_ROOT/daily-report`，缓存键包含日期、内容指纹和模板版本，不依赖 Playwright 或 Chromium。
- 图片接口支持 `scope=full` 与 `scope=focus`：`full` 保留完整日报，`focus` 只渲染当天焦点头版并放大正文，供群聊机器人使用。图片渲染器按赛事标签、对阵标题、单行赛果和解读正文拆分比赛票据；同组主客两场比分固定在一个 SVG 文本行内，超长时自动缩小字号而不换行，解释文字再按卡片真实可用宽度排到下方。比分以金色数据字强调，球队名提高字重，并能从帽子戏法、梅开二度、多次助攻、传射建功、本场最佳及伤停句式中识别和高亮球员姓名；焦点自动稿会保留每组最重要的一条球员高光。机器人正常回复只包含日报标题与 `scope=focus` 图片；只有图片发送失败时才发送 `focus_content` 文字。
- `services/team_name_service.py` 维护当前三级联赛 54 支球队的常见中文名和历史简称映射。自动稿生成后统一本地化球队名；公共读取历史已发布稿时也在响应层转换并生成新的展示指纹，因此无需重写数据库里的人工原稿。工作台读取仍保留原始可编辑正文。
- 当日数据按 `updated_at` 的北京时间自然日读取，适合赛果补录和修正场景；文案使用“今日更新”而不宣称比赛一定在当天进行。当前数据没有进球时间，因此禁止生成逆转、绝杀、补时等无法验证的叙述。
- 联赛与杯赛分别按赛事和同一对手聚合当天更新的主客两场；合并只影响日报叙述，两个回合的轮次、主客方向和比分在票据中逐场保留，积分榜仍对每场比赛独立计分。联赛焦点复用实时排名预测：按前二、前五和后五概率识别争冠、升级与保级竞争球队，再叠加帽子戏法、净胜球、总进球和战力反差评分。赛季后段及收官冲刺自动把相关赛果标记为“争冠关键战 / 升级关键战 / 保级关键战”，完整日报还会列出下一轮预测关键战；头版最多 6 组，并优先保留三类竞争新闻，其余比赛进入常规战报。
- 两回合焦点叙述先总结“两战全胜 / 双方各取一胜 / 两回合保持不败 / 两回合均战平”，再逐一说明首回合和次回合的主客场、胜方比分与比赛形态；比赛形态包括一球险胜、大比分取胜、零封横扫、进球大战和反客为主。单场焦点同样保留对应的比赛形态描述，不再因为生成焦点浓缩稿而只剩平淡结论。
- 自动稿按比赛形态选择险胜、普通胜利、大胜、零封大胜、高比分胜利、闷平、普通平局、高比分平局、单方判负或双方判负主句，再从帽子戏法、梅开二度、多次助攻、传射建功、本场最佳和战力反差中选择一个重点补句。模板通过日报日期、比赛 ID 和类别稳定选取，刷新不会随机改变文本。
- 工作台“每日日报”仅完整管理员可维护：生成操作会保存可继续编辑的草稿；保存草稿不公开，发布后首页、公开接口和机器人优先读取人工终稿。没有人工发布稿时，公开接口返回自动稿；自动稿缓存 180 秒以降低球队战力汇总开销。
- `daily_report_narrative_templates` 保存话术分类、名称、正文、启用状态和排序；后台支持新增、编辑、启停和删除，并校验 `{winner}`、`{loser}`、`{score}`、`{total_goals}`、`{player}`、`{team}`、`{goals}`、`{assists}` 等占位符。话术变更在下一次重新生成时生效，并清除自动稿缓存。
- `daily_reports` 每个日期只保存一份人工稿，状态为 `draft / published`，同时保存统计快照和内容指纹。生成、保存、发布及话术维护均写入操作审计。
